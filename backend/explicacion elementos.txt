models.py       → qué datos existen
serializers.py  → cómo se transforman a JSON
views.py        → qué endpoint usa qué serializer
urls.py         → qué ruta llama a qué viewset
services.py     → dónde se calculan medidas
admin.py        → cómo se gestionan datos desde admin
signals.py      → automatismos
settings.py     → apps instaladas, CORS, DRF
frontend        → cómo Nuxt consume Django

===================== FLUJO COMPLETO =====================
Nuxt page
  -> useFetch("http://127.0.0.1:8000/api/...")
  -> Django backend_led/urls.py
  -> products/urls.py
  -> ViewSet en products/views.py
  -> Serializer en products/serializers.py
  -> Model en products/models.py
  -> SQLite db.sqlite3
  -> Serializer convierte modelo a JSON
  -> Nuxt recibe data/pending/error
  -> template pinta modelos o variantes


===================== Endpoints Actuales =====================

| `GET /api/products/`          | `ProductVariantViewSet`       | `ProductVariantSerializer`        | Alias temporal legacy               |

========================================== Dependencias Importantes ==========================================
- `ProductVariant` depende de `ProductFamily`.
- `ConfigurationProject` depende de `User`, `ProductVariant` y opcionalmente `Controller`.
- `UserProfile` depende de `User` y guarda `can_view_prices`.
- `serializers.py` controla qué sale como JSON y oculta precios.
- `views.py` decide qué queryset atiende cada endpoint.
- `services.py` centraliza cálculos y permiso de precios.
- `signals.py` crea `UserProfile` automáticamente.
- Nuxt consume ahora:
  - `/api/led-models/` en `products/index.vue`
  - `/api/led-models/{slug}/` en `products/[slug].vue`

La idea mental es esta:
settings.py activa la app
↓
urls.py recibe la ruta
↓
views.py decide qué datos buscar
↓
models.py define esos datos
↓
serializers.py los convierte a JSON
↓
Nuxt los recibe
↓
Vue los pinta

Aunque para estudiar, lee primero models.py antes que views.py, porque si no sabes qué datos existen, las views no se entienden bien.
